2 ЗАВДАННЯ
     
     Необхідно показати як можна масштабувати бекенд системи для роботи із великим навантаженням. Для цього, можна на вибір: - масштабувати сервер горизонтально - багато копій сервера виконують однакові функції для різних користувачів; - масштабувати сервер вертикально - різні мікросервіси виконують різні функції і масштабуються окремо одне від одного. З технічної точки зору, масштабування можна виконати так: - деплой сервера на Kubernetes кластер, разом із окремим load balancer-ом та базою даних. При цьому треба буде показати коректну роботу системи при збільшенні чи зменшенні кількості подів сервера чи окремих мікросервісів; - деплой в serverless середовище (AWS Lambda, Firebase Cloud Functions або аналогічне). Треба показати що система може зменшувати кількість активних інстансів до 0, збільшувати її зі збільшенням трафіку і все ще коректно функціонувати. - ваш власний спосіб показати що система може масштабуватись. На найвищий бал на цю роботу необхідно провести навантажувальне тестування за допомогою Gatling, JMeter, Locust чи іншого подібного інструмента і показати як зі збільшенням кількості серверів зростає кількість запитів на секунду яку витримує система

     3 ОПИС ВИКОНАНОЇ РОБОТИ
       
     Для забезпечення стабільної роботи платформи Agrosense (яка передбачає обробку великої кількості телеметрії з IoT-датчиків та запитів від користувачів) було обрано стратегію горизонтального масштабування (Horizontal Scaling).
     На відміну від вертикального масштабування (збільшення CPU/RAM одного сервера), горизонтальне масштабування передбачає запуск кількох однакових копій бекенд-додатка, між якими розподіляється вхідний трафік.
     Вибір цієї стратегії зумовлений архітектурними особливостями Node.js. Оскільки Node.js виконує JavaScript-код в одному потоці (Single-threaded Event Loop), інтенсивні обчислення (наприклад, криптографічне хешування паролів під час авторизації) блокують виконання інших запитів. Горизонтальне масштабування дозволяє обійти це обмеження: розгортання N екземплярів сервера дозволяє обробляти запити паралельно на N процесорних ядрах, забезпечуючи лінійне зростання пропускної здатності системи.
     Для реалізації горизонтального масштабування було використано сучасний стек DevOps-технологій:
     1. Контейнеризація (Docker): Бекенд-додаток (Node.js/Express) було упаковано в ізольований Docker-образ (agro-api:v2). Це гарантує, що кожна копія сервера має ідентичне середовище виконання (залежності, версію Node.js) і є stateless (не зберігає локального стану). Авторизація реалізована через JWT-токени, що дозволяє будь-якому серверу обробити запит від будь-якого користувача.
     2. Оркестрація (Kubernetes): Управління життєвим циклом контейнерів передано кластеру Kubernetes (K8s).
     Використано сутність Deployment, яка дозволяє декларативно вказати бажану кількість копій сервера (replicas: 4). Kubernetes автоматично слідкує за тим, щоб усі 4 поди (Pods) працювали, і у разі падіння одного з них - автоматично запускає новий.
     3. Балансування навантаження (Nginx / K8s Service): Для рівномірного розподілу запитів від клієнтів (IoT-пристроїв та веб-додатку) до 4 екземплярів API було розгорнуто балансувальник Nginx. Він працює як API Gateway (шлюз) і за допомогою алгоритму Round-Robin по черзі направляє HTTP-запити на доступні поди, запобігаючи перевантаженню окремих вузлів.
     4. Єдина база даних (PostgreSQL): Усі репліки API підключаються до єдиного інстансу реляційної бази даних, що забезпечує консистентність даних (Data Consistency) у масштабованій системі.
     Під час проведення навантажувального тестування було виявлено ресурси, які вичерпуються першими при зростанні трафіку:
     1. Процесорний час (CPU) сервера Node.js: При роботі системи в режимі 1 екземпляра (Baseline), першим вузьким місцем стає Event Loop у Node.js. Під час виконання "важких" запитів (ендпоінт /api/v1/auth/login, що використовує хешування паролів bcrypt), процесор завантажується на 100%. Сервер не встигає приймати нові з'єднання, що призводить до відкидання пакетів (помилки ConnectionResetError та RemoteDisconnected).
     2. Мережеві тунелі (Localhost Port-Forwarding): При досягненні показника у ~120 RPS (Requests Per Second) через локальний інструмент дебагу (kubectl port-forward) було зафіксовано помилки Timeout occurred. Це свідчить про те, що локальний мережевий міст не витримує промислового навантаження. У Production-середовищі це вузьке місце усувається використанням хмарних балансувальників (AWS ELB / Ingress Controllers).
     3. Пул з'єднань з Базою Даних (DB Connection Pool): Теоретичним наступним вузьким місцем (при подальшому масштабуванні API до 10-20 подів) стане база даних PostgreSQL, яка має ліміт на максимальну кількість одночасних з'єднань. Для вирішення цього в майбутньому знадобиться впровадження PgBouncer або створення Read-Replicas бази даних.
   Для перевірки ефективності масштабування було проведено навантажувальне тестування за допомогою інструменту Locust.
     • Цільовий ендпоінт: POST /api/v1/auth/login (обрано через високе навантаження на процесор та обов'язкове звернення до БД).
     • Параметри тесту: 500 одночасних користувачів, швидкість додавання - 50 користувачів на секунду (Spawn rate).
Етап 1: Базове тестування (Baseline) - 1 екземпляр сервера
     Під час тестування одного екземпляра сервера система швидко досягла межі своїх можливостей. Час відповіді (Response Time) стрімко зростав до кількох секунд, що є неприйнятним для Production-систем.
     Етап 2: Тестування масштабованої системи - 4 екземпляри сервера
     Після застосування команди масштабування в Kubernetes (kubectl scale deployment agro-api --replicas=4) та направлення трафіку через Nginx балансувальник, результати кардинально змінилися:
     • Загальна кількість запитів: ~18581.
     • Відсоток помилок (Failures): 0% (сервери успішно обробили 100% запитів).
     • Пропускна здатність (Throughput): 160.14 RPS (запитів на секунду).
     • Медіанний час відповіді (Median Response Time): 10 ms.
     • Середній час відповіді (Average Response Time): ~48 ms.
